1. REQUIREMENTS                                           *mcp-buff-requirements*

Neovim 0.10 or newer, curl on $PATH, SSH access (or an existing local forward)
to an installed broker admin listener, and a command that can print each
broker's admin capability. McpBuff has no Lua or Neovim plugin dependencies.

It never accepts a Cloudflare token and never calls Cloudflare directly.

Version 2 speaks the hardened admin contract. It is not compatible with a
broker release that predates bearer authentication and digest-bound decisions,
and version 1 is not compatible with a broker that requires them.

==============================================================================
2. INSTALLATION                                           *mcp-buff-installation*

With lazy.nvim: >lua

    {
      "777lotto/mcp-buff",
      main = "mcp_buff",
      cmd = { "McpBuff", "McpBuffPermissions" },
      keys = {
        { "<leader>mb", "<cmd>McpBuff<cr>",
          desc = "Cloudflare write tickets" },
        { "<leader>mp", "<cmd>McpBuffPermissions<cr>",
          desc = "Broker permissions" },
      },
      opts = {
        endpoint = "http://127.0.0.1:8792",
        capability_cmd = { "pass", "show", "your/broker/admin-capability" },
        tunnel = { host = "your-broker-host" },
        permissions = {
          github = {
            capability_cmd = {
              "pass", "show", "your/github/admin-capability"
            },
            tunnel = { host = "your-broker-host" },
          },
        },
      },
    }
<
setup() must be called, because capability_cmd has no default.

3. TUNNEL                                                       *mcp-buff-tunnel*

McpBuff can own a forward for the lifetime of the review panel: >lua

    tunnel = {
      host = "your-broker-host",
      ssh_command = "ssh",
      startup_timeout = 30000,
    }
<
Opening :McpBuff launches one foreground process, with no shell: >

    ssh -N -T -o BatchMode=yes -o ExitOnForwardFailure=yes
      -o ServerAliveInterval=15 -o ServerAliveCountMax=3
      -o ControlMaster=no -o ControlPath=none
      -L 127.0.0.1:8792:127.0.0.1:8792 your-broker-host
<
McpBuff waits for the listener before reading the capability or sending HTTP.
Closing the panel by any route terminates only this SSH child; VimLeavePre does
the same. An in-flight decision keeps the route until its outcome is resolved,
then closes it. McpBuff does not manage an underlying VPN.

Managed mode refuses an already occupied local port. It never sends the admin
capability through a listener whose ownership it cannot prove. Use a dedicated
SSH alias without unrelated configured forwards.

The default, tunnel = false, preserves external lifecycle management. Open the
local forward before starting the panel: >sh

    ssh -N -L 8792:127.0.0.1:8792 you@your-broker-host
<
The forward must be symmetric.                            *mcp-buff-symmetric*

The broker compares the request Host against its own bound socket port, not
against a port you choose. So `-L 8792:127.0.0.1:8792` works and
`-L 9999:127.0.0.1:8792` does not: it satisfies every condition stated in
prose and is still rejected with 400, because the client sends
Host: 127.0.0.1:9999 while the broker's bound port is 8792.

The rule is: make the local forward port equal the broker's admin port, or
override the Host header to the broker's port with the host_header option.

Keep an external SSH process running while reviewing. Stopping it revokes
access. Never bind the local side to 0.0.0.0 or enable gateway forwarding.

4. CAPABILITY                                               *mcp-buff-capability*

Every admin request carries `Authorization: Bearer <capability>`, where the
capability is 64 lowercase hex characters.

capability_cmd is an argv list, run with no shell: >lua

    capability_cmd = { "pass", "show", "your/broker/admin-capability" }
<
The command must print the capability and nothing else. McpBuff keeps the
value in Lua memory only. It never places it in argv, in an environment
variable, on disk, or in any message it prints: the value reaches curl through
a configuration file fed on standard input.

The value is held for capability_ttl seconds so that refreshing the panel does
not re-run the command for every request, and is dropped when the review
session closes, when Neovim exits, and whenever setup() runs again. An
in-flight decision delays teardown until its outcome resolves. A 401 triggers
exactly one forced re-read, in case the capability was rotated mid-session,
and the failure is then surfaced rather than retried.

A failed capability read aborts the request. McpBuff never falls back to
sending an unauthenticated request, because that failure would reach you as an
opaque 401 rather than as "your card is not available".

The background refresh timer never runs capability_cmd.  *mcp-buff-no-prompts*
If the cached value has expired, a timer tick is skipped instead. This makes a
credential prompt storm structurally impossible rather than merely unlikely.
Press r when you want the panel to acquire a capability again.

5. RUNTIME PERMISSIONS                                    *mcp-buff-permissions*

:McpBuffPermissions opens effective runtime switches for the Cloudflare and
GitHub brokers. These switches can only narrow the compiled, reviewed broker
policy. They cannot add an operation, change a route, edit a credential,
alter GitHub App permissions, or expand a Cloudflare API token.

Cloudflare entries correspond one-for-one with compiled mutation operation
IDs. GitHub groups cover MCP, Git read, agent-branch push, reviewed workflow
push, API reads, issue writes, pull-request writes, and gated merge.

Space or Enter toggles a row. Press a to apply the selected provider after
typing the final eight characters of its current state digest. The complete
digest is sent with the desired subset, so a concurrent change answers 409
and must be refreshed. An unaccounted-for POST is never retried; the panel
marks the state unknown and requires a fresh read.

Cloudflare permissions share the main Cloudflare capability and managed
tunnel. GitHub defaults to http://127.0.0.1:8793 and uses a distinct
capability cache and optional tunnel: >lua

    permissions = {
      cloudflare = {},
      github = {
        capability_cmd = {
          "pass", "show", "your/github/admin-capability"
        },
        tunnel = { host = "your-broker-host" },
      },
    }
<
Set either provider to false to hide it. GitHub remains visibly unconfigured
until its capability_cmd is supplied. Broker releases without GET /permissions
and POST /permissions must be upgraded; do not weaken the admin boundary.

6. COMMAND AND KEYS                                          *mcp-buff-commands*

:McpBuff        Open the ticket panel as a left split.
:McpBuffPermissions
                Open the provider runtime-permissions panel as a left split.

The following mappings are local to the panel buffer:

<CR>            Re-fetch and open the full ticket detail. LF and keypad Enter
                perform the same action.
a               Re-fetch, review, and approve a pending ticket after typing
                the digest confirmation.
d               Re-fetch, review, and deny a pending ticket with an optional
                note after typing the digest confirmation.
r               Refresh the ticket list.
q               Close the panel and its managed tunnel. In detail, q or <Esc>
                closes the float.

In the permissions panel, Space or Enter toggles a permission, a applies the
selected provider after typed digest confirmation, r refreshes both providers,
and q closes the panel. An in-flight update retains its owned route until the
outcome is accounted for.

7. REVIEW FLOW                                                 *mcp-buff-review*

The panel groups tickets pending-first, followed by approved, executing,
indeterminate, failed, denied, expired, and executed. Rows show age, the
complete ticket ID, and a reason excerpt.

<CR> opens the full reason, the expiry, the complete ticket_sha256, each
stored request as method, literal path and pretty-printed JSON body, each
request's structured precondition, every preflight observation, and every
result.

A decision never acts from the summary cache. It re-fetches the full ticket,
refuses anything that is not pending, and recomputes ticket_sha256 locally
from the ticket's own immutable fields.

Digest recomputation                                         *mcp-buff-digest*

The digest covers exactly id, created, expires, reason and requests, hashed
as: >

    sha256("zemrip.mcp-ticket.v1" + "\n" + canonicalJson(payload))
<
McpBuff recomputes it and refuses to submit when the result disagrees with the
served value. It also refuses when the payload contains anything it cannot
canonicalise to the same bytes the broker would produce — in practice a
non-integer number or a non-ASCII object key. Refusing is deliberate: a
guessed digest would let you approve a payload you had not actually verified.

What the digest does and does not guard: it catches a cross-ticket replay, a
client-side digest bug, and direct tampering with the stored ticket. It does
not detect a concurrent decision, because the five immutable fields never
change; a ticket approved, denied, or expired between your read and your
submission keeps an identical digest, and that race is caught by the ticket
state machine instead.

Typed confirmation                                          *mcp-buff-confirm*

After the render, McpBuff requires you to type the final eight characters of
the digest: >

    ticket_sha256: 9f2c...a41b7e3d
    Type the final digest bytes a41b7e3d to approve:
<
There is no single-keypress approval and no yes/no prompt. Anything other than
the exact suffix cancels, and nothing is sent.

The plugin cannot edit a ticket and supplies no requests at approval time.

8. DECISION OUTCOMES                                         *mcp-buff-outcomes*

A decision is never resubmitted.                       *mcp-buff-no-resubmit*

Resubmitting cannot execute a ticket twice — the broker's state machine has no
edge back to approved, so a second POST loses and receives a 409. The reason
not to resubmit is that the 409 destroys the account of what happened: it
carries the same shape as an expiry and a denial made elsewhere, and it tells
you only where the ticket stands now, not whether your first submission's
mutations reached Cloudflare.

So when a decision POST fails, times out, or returns a body McpBuff cannot
read, it polls that same ticket every two seconds until it reaches a terminal
state, up to poll_deadline. On the deadline, or if the ticket cannot be
fetched at all, it reports the outcome as unknown and stops.

When the broker refuses the request outright — a gate failure, a 404, or
either 409 — nothing was touched, so the refusal is reported directly and
nothing is polled.

Approval executes synchronously inside the POST, so a 200 from approve is
always terminal. A 200 carrying "approved" or "executing" cannot occur.

Terminal states are executed, failed, indeterminate, denied and expired.

indeterminate                                        *mcp-buff-indeterminate*

indeterminate means the outcome is genuinely unknown: a mutation may or may
not have reached Cloudflare. It is rendered as its own group, never as a
failure, and it is not a retry signal. Inspect it upstream; never replay the
ticket.

Errors you will see                                          *mcp-buff-errors*

The four transport gates have distinct statuses and share one ordered
middleware chain: Origin (403), Host (400), bearer (401), then content type
(415) on POSTs only. A status names the first gate that failed, not the worst
thing wrong with the request, so a bad Host masks a missing capability and
answers 400 rather than 401. Fix them in that order.

A 400 carrying "invalid host" is a configuration fault — an asymmetric
forward. It is never a retryable body error, and it must not prompt you to
resubmit a decision.

Both 409s share a status and are separated only by their message text: one is
a digest mismatch, the other is a state transition that is no longer legal,
which after a pending render means the ticket expired or was decided while you
were reviewing.

A 500 on a decision may be nothing worse than a note over the broker's 32kb
body cap, so it is treated as an unknown outcome and polled.

An off-route request returns HTML rather than JSON. McpBuff decodes error
bodies defensively and reports this as a wrong route, not as a JSON error.

A terminal ticket is unlinked once it is past the broker's retention window
and then 404s. Listing tickets is what expires the overdue and prunes the
aged, so the list itself is not a pure read.

9. CONFIGURATION                                             *mcp-buff-config*

Default configuration: >lua

    require("mcp_buff").setup({
      endpoint = "http://127.0.0.1:8792",
      capability_cmd = nil,     -- required; argv list, run with no shell
      capability_ttl = 300,     -- seconds the value is held in memory
      curl_command = "curl",
      timeout = 30000,          -- milliseconds; reads only
      decision_timeout = 1865,  -- seconds; the approve/deny POST
      poll_deadline = 1865,     -- seconds; outcome polling after a failed POST
      refresh_interval = 0,     -- seconds; automatic refresh is off
      host_header = nil,        -- e.g. "127.0.0.1:8792" for an asymmetric forward
      tunnel = false,           -- or { host = "broker-ssh-alias" }
      permissions = {
        cloudflare = {},        -- inherits the main Cloudflare session
        github = {
          endpoint = "http://127.0.0.1:8793",
          capability_cmd = nil, -- distinct GitHub admin capability
          tunnel = false,
        },
      },
    })
<
endpoint must use the exact shape http://127.0.0.1:PORT. Remote, bridge,
HTTPS, path-bearing, and credential-bearing values are rejected.

timeout applies to reads only. A read performs no execution, so a read that
hangs for half an hour is a broken tunnel, not a long approval.

decision_timeout applies to the approve and deny POST, and is clamped to
65..86400 seconds. Approval performs every preflight GET and every mutation
inside that one request: up to ten requests, each incurring two preflight GETs
and a mutation, each individually timed at the broker's own 60s default. The
worst case is far longer than a conventional HTTP timeout, which is why the
default is 1865 rather than 30.

Neither timeout bounds your review time. That is bounded only by the ticket's
expiry, which the detail view always shows.

poll_deadline bounds the outcome polling described in |mcp-buff-outcomes| and
is clamped to the same range.

A positive whole refresh_interval enables the optional background timer, which
never runs capability_cmd; see |mcp-buff-no-prompts|. Manual r remains
available. In managed mode, the timer runs only while the panel is visible and
never reopens a route after the panel closes.

host_header overrides the Host header for an asymmetric forward; see
|mcp-buff-symmetric|. Making the forward symmetric is preferred.

tunnel enables the optional panel-scoped SSH lifecycle. host is required and
must be an SSH alias or hostname without whitespace. ssh_command defaults to
"ssh", and startup_timeout defaults to 30000 milliseconds and accepts
1000..120000. Unknown keys are rejected. The endpoint port supplies both sides
of the symmetric loopback forward.

permissions.cloudflare is {} by default and inherits the main Cloudflare
endpoint, capability, and tunnel. It may be false to hide that provider.

permissions.github defaults to endpoint http://127.0.0.1:8793 and has no
capability_cmd or tunnel. Supply its own capability_cmd and, when desired, its
own managed tunnel. It may be false to hide GitHub. The two provider
capabilities are never shared.

10. LUA API                                                        *mcp-buff-api*

The module is returned by: >lua

    local buff = require("mcp_buff")
    buff.setup({ capability_cmd = { "pass", "show", "entry" } })
    buff.open()
    buff.open_permissions()
    buff.refresh()
    buff.pending_count()
    buff.close()
<
pending_count() is nonblocking and returns the latest cached count. It returns
0 before the first successful refresh. This makes it safe for statuslines.

11. SECURITY                                                  *mcp-buff-security*

McpBuff speaks only the loopback broker admin API through curl. Curl user
configuration and redirects are disabled, the endpoint is syntactically
restricted to IPv4 loopback, and no shell is involved anywhere, including the
capability fetch and managed SSH launch.

The capability is the only secret in play, and it travels on the private
channel: a curl configuration file on standard input. The decision body is not
secret — it carries the digest and an optional note — and travels through
ordinary process arguments. Note that process arguments are visible to other
processes running as your user, so do not type anything into a denial note
that you would not put in `ps` output.

Panel and detail buffers are nofile with swap files and undo files disabled,
so ticket bodies and Cloudflare responses do not reach swap, undo, or log
files. The plugin persists nothing.

McpBuff has no GitHub or Cloudflare API client, no zemRip dependency, and
nowhere to configure a provider token. Permission updates contain only the
current state digest and a subset of IDs advertised by that same provider;
GitHub and Cloudflare capabilities remain in isolated caches. Never weaken a
broker, expose its admin listener, or move a capability somewhere more
convenient in order to restore compatibility with an older client.

Managed mode creates a symmetric loopback-only forward, disables SSH control
multiplexing for exact process ownership, and refuses to reuse an existing
listener. The SSH account and local forward remain the authority boundary.
Managed mode closes its route with the review session; external mode leaves
that responsibility to the operator.

==============================================================================
12. DEVELOPMENT                                            *mcp-buff-development*

Linux is tested on Neovim 0.10, 0.11, and 0.12. macOS is smoke-tested on
Neovim 0.12. The dependency-free Node stub in scripts/stub-admin-server.js
implements the hardened admin contract — the four gates in order, strict
decision and permission schemas, digest binding, synchronous terminal
approval, lazy expiry, retention pruning, HTML off-route bodies, and the
32kb-to-500 behaviour — so the headless suite exercises the real contract over
real curl. No test reaches a broker host or provider.

The canonical JSON test vectors are copied verbatim from the broker's own
suite. If the two implementations ever disagree, the unit tests fail before
anything can be submitted.

Development branches start from and merge into bluff. Tested releases promote
bluff into bet.
